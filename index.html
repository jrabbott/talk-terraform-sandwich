Terraform

What is Terraform?

Infrastructure as code: declare cloud and SaaS resources in versioned files, then plan and apply changes through one consistent workflow.

  • Configuration describes the desired state
  • State tracks what already exists
  • Providers translate that into API calls
Keep this short. The talk is about the sandwich pattern, not a full Terraform workshop.
Terraform never talks to Azure or AWS directly — the provider does.

Why use Terraform?

  • Manage any infrastructure
  • Track your infrastructure
  • Automate changes
  • Standardise configurations
  • Collaborate

When love and hate collide

Teams love declarative IaC. They hate it when create-time dependencies need a live application that Terraform cannot bring up in the same apply.

Terraform Sandwich

A multi-stage Terraform pattern: run Terraform more than once in a CI/CD pipeline, with an application release between the stages.

  • Stage 1 creates everything safe to provision first
  • Release deploys and starts the application
  • Stage 2 creates resources that need the app to be alive
Corrected from the source deck typo “more and one” → “more than once”.

For example: Azure Event Grid

Event Grid validates the Azure Function endpoint when the subscription is created — function code must already exist, not just the Function App.

  • You cannot create the subscription until the function (with its name and metadata) is deployed
  • You cannot deploy that function until the Function App is provisioned
  • A single greenfield apply hits a circular dependency
From Mark Tinderholt’s “Terraform Apply Sandwich” write-up: empty Function App ≠ healthy Event Grid trigger. Waiting inside one Terraform run couples infra to app deploy timing and still fails validation on first create.

What fails on first apply

Azure rejects the subscription while polling CreateOrUpdate — Terraform exits with code 1.

  • Code: Endpoint validation
  • Message gist: destination endpoint not found — the function resource should pre-exist
  • Typical path ends in …/functions/<FunctionName>
Real error shape: Status Failed, Code “Endpoint validation”, Message “Destination endpoint not found. Resource details: resourceId: …/sites/func-…/functions/InternalSubscriber. Resource should pre-exist before attempting this operation.” The Function App may already exist; the named function does not yet.

Solution

  • Terraform 1: Function App + topic; subscriptions disabled (eventgrid_subscriptions_enabled = false)
  • Release: deploy the named function so it is discoverable
  • Terraform 2: enable the flag and create the subscriptions
Gate subscription resources only on bootstrap. Flipping the flag back to false later can destroy live subscriptions via count.

Gate with count

Conditionally include the subscription until the function endpoint can pass validation. 


resource "azurerm_eventgrid_event_subscription" "internal" {
  count = var.eventgrid_subscriptions_enabled ? 1 : 0

  name  = "evgs-${var.name}-${var.location}-internal"
  scope = azurerm_eventgrid_topic.main.id

  azure_function_endpoint {
    function_id = local.eventgrid_internal_subscriber_endpoint
  }
}
First apply with the flag false; deploy code; second apply with true. Prefer a create-gate over casually toggling count in production pipelines.

When to use it

  • Use when create depends on deployed app behaviour or a live endpoint
  • Mostly a first-bring-up problem — later deploys are one-pass if the function name stays stable
  • Keep shared state clear between the two Terraform stages
  • Avoid it when a single apply (or a provisioner-free redesign) is enough
Prefer redesigning the dependency when you can. The sandwich is a pragmatic escape hatch for ordering constraints CI already owns. Expect a window without subscriptions while the flag is off — events are not routed until Terraform 2 succeeds. Renaming the function can force the sandwich again.
