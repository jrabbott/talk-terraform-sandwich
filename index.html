Terraform

What is Terraform?

Infrastructure as code: declare cloud and SaaS resources in versioned files, then plan and apply changes through one consistent workflow.

  • Configuration describes the desired state
  • State tracks what already exists
  • Providers translate that into API calls
Keep this short. The talk is about the sandwich pattern, not a full Terraform workshop.
Terraform never talks to Azure or AWS directly — the provider does.

Why use Terraform?

  • Manage any infrastructure
  • Track your infrastructure
  • Automate changes
  • Standardise configurations
  • Collaborate

When love and hate collide

Teams love declarative IaC. They hate it when create-time dependencies need a live application that Terraform cannot bring up in the same apply.

Terraform Sandwich…

…is a multi-stage Terraform pattern: run Terraform more than once in a CI/CD pipeline, with an application release between the stages.

  • Stage 1 creates everything safe to provision first
  • Release deploys and starts the application
  • Stage 2 creates resources that need the app to be alive
Corrected from the source deck typo “more and one” → “more than once”.

For example: Azure Event Grid

Problem

An Azure Functions app must be released and running before Terraform can create the Event Grid subscription that points at it.

  • A single apply cannot create the subscription first — the endpoint is not there yet
  • Waiting inside one Terraform run couples infra to app deploy timing

Solution

Terraform 1 creates everything except Event Grid subscriptions; release the app; Terraform 2 creates the subscriptions.

When to use it

  • Use when create depends on deployed app behaviour or a live endpoint
  • Keep shared state clear between the two Terraform stages
  • Avoid it when a single apply (or a provisioner-free redesign) is enough
Prefer redesigning the dependency when you can. The sandwich is a pragmatic escape hatch for ordering constraints CI already owns.
